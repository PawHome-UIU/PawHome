====================================================================================================
 PAWHOME - RELATIONAL SCHEMA (MySQL)
 Pet Adoption & Boarding Management System
====================================================================================================

 Course      : CSE 3522 - Database Management Systems Laboratory, UIU
 Engine      : MySQL 8.4  |  ENGINE=InnoDB  |  utf8mb4 / utf8mb4_0900_ai_ci
 Derived from: PawHome Figma design (30 screens) + stakeholder brief
 Generated   : 2026-08-30

 32 tables  |  2 views  |  8 modules  |  69 foreign keys
 313 columns  |  39 CHECK constraints  |  19 UNIQUE keys  |  124 indexes

 NOTE - this document describes V1. Several migrations have run since it was
 generated; the counts above are current, the table bodies below are not:

   V4  adds users.email_verified, and the tables user_tokens and
       health_reminders_sent (25 -> 27 tables, 51 -> 53 foreign keys).
   V5  widens user_tokens.token_hash from CHAR(64) to VARCHAR(64), so it
       matches what the JPA entity declares.
   V6  makes the quiz type part of the relationship. quiz_attempts gains
       UNIQUE(id, quiz_type); adoption_applications and boarding_requests
       each gain a constant type column and reference the pair, so the
       wrong kind of attempt can no longer be attached. quiz_attempts
       .score / .max_score / .passed become nullable, with a CHECK that
       ties them to the type: scored for ELIGIBILITY and BOARDING, null
       for PERSONALITY.

   V9  makes pets.shelter_id nullable and adds the OWNED status, so a pet
       that has never been in a shelter can be boarded by the household
       that has always owned it.
   V15 adds the two facts nothing recorded: daycare_attendance (who is in
       the building today, and in which room) and billing_slip_items (what a
       bill says besides the nights). 29 -> 31 tables.

       daycare_attendance is why the staff "Pets in Care" tile was wrong: it
       rendered pet_count, which is the shelter's BOOKS, under a label
       everyone read as the shelter's BUILDING. A boarded pet belongs to a
       household, has no shelter_id, and was never on those books -- so
       accepting two boarding requests moved the number not at all.

   V17 gives a stay somewhere to put an EXPENSE WHILE IT IS HAPPENING.
       boarding_charges (31 -> 32 tables, 67 -> 69 foreign keys). Before it,
       the only place to record the Tuesday worming tablet was the check-out
       dialog on Friday -- billing_slip_items hangs off a slip, and a slip
       does not exist until the stay is completed.

       TWO TABLES FOR TWO LIFECYCLES, not duplication. boarding_charges is
       ACCRUING -- staff add, correct and remove it while the animal is here,
       and nobody has been billed. billing_slip_items is FROZEN, a line on an
       issued bill. complete() copies the first into the second, which is the
       same freeze daily_rate and unit_rate already get: money a customer has
       been quoted stops moving.

   V18 adds ROOM_CHANGE to boarding_updates.update_type, so a pet moved
       between rooms mid-stay says so on the stay's own timeline. APPENDED at
       the end: MySQL stores an ENUM as the INDEX of the value, so inserting
       one in the middle would renumber every value after it and silently
       change what existing rows mean. Verified -- the original six keep 1..6
       and ROOM_CHANGE is 7.

   V16 gives a room a SIZE. shelter_suites gains capacity (282 columns,
       37 CHECKs), and daycare_attendance loses uq_suite_band (20 -> 19
       UNIQUE keys) in exchange for idx_attendance_suite_band, so the index
       count is unchanged.

       THE POINT IS WHAT MOVED OUT OF THE SCHEMA. uq_suite_band said "one
       animal per room per band", which is the right rule for a kennel and
       the wrong one for a twenty-place cat loft. The replacement rule --
       "no more animals than shelter_suites.capacity" -- counts rows in TWO
       tables against a column in a THIRD, which no MySQL constraint can
       express: a CHECK may not contain a subquery, a UNIQUE key counts to
       exactly one, and there is no EXCLUDE. So it lives in a transaction
       with SELECT ... FOR UPDATE, alongside the boarding overlap rule V1
       handed over for the same reason. See docs/TRANSACTIONS.txt.

       The same shape appears one level up: shelters.capacity is the
       building's licensed headcount, and BoardingService.accept now locks
       the shelters row before counting residents plus boarders against it.
       A shelter at its licence refuses the stay and the staff member
       declines with NO_CAPACITY, which DeclineReason has carried since V1.

   V13 adds the BILLING half: daycare_subscriptions and billing_slips
       (27 -> 29 tables, 53 -> 62 foreign keys), two daycare columns on
       shelters, boarding_requests.picked_up_on, and SLIP_ISSUED on the
       notifications.type ENUM.

       There is NO payment processing anywhere in it -- no gateway, no card
       storage, no PAID flag. A slip records what is owed and stops; the
       cash is handed over at the counter. That is a scope decision, not an
       omission: see docs/BILLING_DESIGN.txt.

 The migrations under backend/src/main/resources/db/migration are the
 authority. So is docs/pawhome-erd.drawio, which is generated from them.

----------------------------------------------------------------------------------------------------
 LEGEND
----------------------------------------------------------------------------------------------------

   PK   primary key                FK   foreign key
   PF   composite PK that is also a FK (junction tables)
   U    unique constraint

   Conventions applied throughout:
     - BIGINT AUTO_INCREMENT surrogate key on every non-junction table.
       Signed, not UNSIGNED: an UNSIGNED PK with a signed FK is MySQL
       errno 150 and a confusing hour. Signed BIGINT is plenty at this scale.
     - DATETIME (never TIMESTAMP) for instants, always stored in UTC.
       MySQL has no timezone-aware type; TIMESTAMP converts by session
       timezone and overflows in 2038.
     - DECIMAL for money. Never FLOAT or DOUBLE.
     - ENGINE=InnoDB on every table - required for foreign keys AND for
       the transactions the course rubric requires.
     - CHECK constraints are enforced from MySQL 8.0.16. Pin the Docker
       image to mysql:8.4 - older servers PARSE and SILENTLY IGNORE them.

  ....................................................................................................
   TABLE  shelter_suites
  ....................................................................................................
   Named boarding spaces. From 'Suite 4' / 'Kitty Loft' on the boarding cards.

   KEY  COLUMN                   TYPE                           NULL      CONSTRAINTS / NOTES
   ---- ------------------------ ------------------------------ --------- ------------------------------
   PK   id                       BIGINT                         NOT NULL  AUTO_INCREMENT
   FK   shelter_id               BIGINT                         NOT NULL  -> shelters(id) ON DELETE CASCADE
        name                     VARCHAR(60)                    NOT NULL  UNIQUE (shelter_id, name)
        species                  ENUM(3)                        NULL      NULL = any species
        is_active                BOOLEAN                        NOT NULL  DEFAULT TRUE
        capacity                 INT                            NOT NULL  V16. DEFAULT 1. CHECK (> 0 AND <= 500)

   ENUM COLUMN DEFINITIONS:
     species                ENUM('DOG', 'CAT', 'OTHER')

   capacity IS NOT shelters.capacity. That one is the whole building's
   licensed headcount -- the denominator of the "28 / 50" bar. This is the
   denominator of ONE ROOM's bar. The sum of the second should not exceed the
   first, and that is deliberately NOT a constraint: a shelter mid-renovation
   with the rooms entered and the licence not yet raised would be locked out
   of its own record by something that is really a policy.

   DEFAULT 1 reproduces exactly the pre-V16 behaviour -- one animal per room
   -- so a suite nobody has sized refuses a second occupant rather than
   accepting an unbounded number.

   NOTES:
     - NO-DOUBLE-BOOKING IS NOT A CONSTRAINT IN MYSQL.
       PostgreSQL would express it declaratively with EXCLUDE USING gist.
       MySQL has no equivalent, so the guarantee moves into a TRANSACTION:
           START TRANSACTION;
           SELECT id FROM boarding_requests
            WHERE pet_id = ? AND status IN ('ACCEPTED','ACTIVE')
              AND start_date <= ? AND end_date >= ?   -- overlap test
            FOR UPDATE;
           -- if any row returned -> ROLLBACK and reject
           UPDATE boarding_requests SET status='ACCEPTED', suite_id=? WHERE id=?;
           COMMIT;
       This is the course's required BEGIN/COMMIT/ROLLBACK feature.
       idx_boarding_overlap exists to shorten the lock this holds.

  ....................................................................................................
   VIEW  v_pet_listing
  ....................................................................................................
   The single reusable listing projection. Consumed by FOUR pages:
   guest browse, adopter browse, favourites, and staff Manage Pets.

     pet_id, name, species, breed, age_value, age_unit, sex, size, status,
     shelter_id, shelter_name, shelter_city,
     cover_photo_path        from pet_photos WHERE is_cover
     trait_labels            GROUP_CONCAT over pet_traits -> traits.label
                             (MySQL's GROUP_CONCAT replaces Postgres string_agg;
                              raise group_concat_max_len if labels are truncated)
     is_vaccinated           DERIVED: has >= 1 COMPLETED vaccination AND no
                             SCHEDULED row with next_due_on < CURDATE()
     open_application_count  COUNT of PENDING adoption_applications

   Why a view: four pages rendered the same joined shape. One definition means
   the vaccination rule cannot drift between the guest page and the staff page.

   MySQL note: a view's SELECT has more restrictions than Postgres allows.
   Build it with plain JOINs and window/aggregate functions rather than
   derived tables in the FROM clause, and verify it creates before relying on it.

  ....................................................................................................
   VIEW  v_adopter_traits
  ....................................................................................................
   An adopter's derived trait set - the 'YOUR TRAITS' chip row on Recommendations.

     user_id, trait_id, trait_label
       FROM quiz_attempts (latest PERSONALITY attempt per user)
       JOIN quiz_answers -> quiz_options -> option_traits -> traits

   Why a view and not a table: it is fully derived from data already stored.
   Materialising it would be a 3NF violation whose only justification is speed,
   and the personality quiz is taken rarely enough that speed is not a problem.

   MATCH SCORE (computed in Java, stored nowhere):
     weighted overlap between v_adopter_traits and pet_traits over the same
     seven-value vocabulary, normalised to 0-100. A pure function of two sets,
     so it unit-tests cleanly and explains itself:
       '92% - matched on Energetic, Affectionate, Playful; missed Independent'


====================================================================================================
 SECTION 4 - INDEXES
====================================================================================================

 Beyond the automatic PRIMARY / UNIQUE / foreign-key indexes InnoDB creates:

   uq_pet_cover          UNIQUE (cover_key) ON pet_photos
                         cover_key is a STORED generated column, NULL unless
                         is_cover. NULLs never collide in a MySQL unique index,
                         so this enforces exactly one cover photo per pet.

   uq_one_open_app       UNIQUE (applicant_id, pending_key)
                         ON adoption_applications. Same generated-column
                         technique: one OPEN application per person per pet,
                         while many people may still apply for the same pet.

   idx_pets_browse       (status, species, size) ON pets
                         JUSTIFICATION: the browse page filters on exactly these
                         three columns and reports '248 pets found'. Without the
                         index every filter change is a full table scan.

   idx_boarding_overlap  (pet_id, start_date, end_date) ON boarding_requests
                         JUSTIFICATION: the date-overlap check runs on every
                         accept, INSIDE a transaction holding SELECT ... FOR
                         UPDATE row locks. This index shortens the lock window,
                         not merely the query. ** This is the index to write up
                         for the course requirement - show EXPLAIN before/after. **

   idx_apps_queue        (status, submitted_at DESC) ON adoption_applications
                         The staff review queue sorts pending by date.

   idx_care_due          (status, due_at) ON care_tasks
                         'Today's Care Tasks' and the overdue count.

 SECTION 6 - NORMALISATION (3NF) AND DOCUMENTED EXCEPTIONS
====================================================================================================

 All 25 tables are in Third Normal Form except the four column groups below.
 Each exception is deliberate and shares one justification shape:

      THIS COLUMN IS A HISTORICAL RECORD, NOT A CURRENT FACT.

 -------------------------------------------------------------------------------------------------
 1. adoption_applications.applicant_name / _email / _phone / _address / _city
    Transitively dependent on applicant_id -> users.
    JUSTIFICATION: an application is a document a staff member reviewed and
    signed off. If the adopter later moves house, last year's approved
    application must still show the address it was approved against.
    Normalising it would silently rewrite a reviewed record.

 2. adoption_applications.quiz_score
    Derivable from quiz_attempts.
    JUSTIFICATION: admins can edit option weights at any time, so recomputing
    an old score would change it. Frozen at submission, like a printed mark.

 3. adoptions.shelter_id
    Reachable via pet_id -> pets.shelter_id (transitive dependency).
    JUSTIFICATION: 'Adoptions by Shelter' must credit the shelter that
    performed the adoption even if the pet is later transferred.

 4. boarding_requests.daily_rate / estimated_cost
    Derivable from shelters.boarding_rate_daily.
    JUSTIFICATION: a price quoted to a customer must not change retroactively
    when the shelter updates its rate.
 -------------------------------------------------------------------------------------------------

 NOT counted as exceptions - generated columns:
   pet_photos.cover_key and adoption_applications.pending_key are STORED
   GENERATED columns, not independent facts. They exist only because MySQL
   lacks partial indexes; their value is a pure function of columns in the
   same row, so they introduce no transitive dependency.

 TWO THINGS DELIBERATELY *NOT* STORED, to stay in 3NF:

   pets.is_vaccinated   - derived in v_pet_listing from the vaccination records.
                          Storing it is how a pet ends up showing a green tick
                          beside an overdue shot.

   adopter trait set    - exposed as the view v_adopter_traits rather than a
                          materialised table. Removes the exception and supplies
                          the reusable VIEW the course requires.

 ALSO DERIVED, NEVER STORED:
   - 'OVERDUE' care task     = status 'PENDING' AND due_at < NOW()
   - 'Overdue' vaccination   = status 'SCHEDULED' AND next_due_on < CURDATE()
   - Shelter occupancy       = COUNT(pets) against shelters.capacity
   - Average review time     = AVG(TIMESTAMPDIFF(DAY, submitted_at, reviewed_at))
   - Match score             = overlap(v_adopter_traits, pet_traits)

 SECTION 7 - COURSE SQL COVERAGE MAP
====================================================================================================

 Each rubric requirement, and the application feature that produces it.
 All seven are demonstrated through real features, not standalone scripts.

 DML .......... INSERT  Add Pet, Add Vaccination, submit application
                UPDATE  approve application, edit pet, deactivate shelter
                SELECT  every listing page
                DELETE  un-hearting a pet on the Favorites page - the one place
                        a hard delete is correct, because a removed favourite
                        has no historical value

 AGGREGATION .. Analytics & Reports page:
                  COUNT(*)  ... GROUP BY shelter_id       -> Adoptions by Shelter
                  COUNT(*)  ... GROUP BY species, status  -> Pets by Species/Status
                  AVG(TIMESTAMPDIFF(DAY, submitted_at, reviewed_at))
                                                          -> 'AVG REVIEW TIME 2.4 days'
                HAVING: the Shelters Overview capacity alert -
                  GROUP BY s.id HAVING COUNT(p.id) >= 0.9 * s.capacity

 JOINS ........ INNER JOIN  applications -> users -> pets -> shelters
                            (the staff Applications table)
                LEFT JOIN   the 'Overdue Vaccinations' tile must count pets with
                            NO vaccination record at all, alongside pets whose
                            shot is overdue. An INNER JOIN silently hides the
                            never-vaccinated ones - the worst cases. LEFT JOIN
                            here is a correctness requirement, not a demo.

 SUBQUERY ..... Recommendations must not suggest a pet the adopter already has
                an open application for - a CORRELATED subquery:
                  WHERE NOT EXISTS (SELECT 1 FROM adoption_applications a
                                    WHERE a.pet_id = p.id
                                      AND a.applicant_id = ?
                                      AND a.status = 'PENDING')

 VIEW ......... v_pet_listing, used by four pages (Section 3).

 TRANSACTION .. Two, both genuinely needed:
                (a) Approving an adoption application - five steps that must
                    all succeed or all roll back:
                      1. UPDATE adoption_applications SET status='APPROVED'
                      2. INSERT INTO adoptions ...
                      3. UPDATE pets SET status='ADOPTED', owner_id=...
                      4. UPDATE the pet's other PENDING applications -> REJECTED
                      5. INSERT INTO audit_log ...
                    Without it a mid-way failure leaves a pet marked ADOPTED
                    with no adoption record, or two adopters approved for one pet.

                (b) Accepting a boarding request - SELECT ... FOR UPDATE overlap
                    check. See the boarding_requests notes. In PostgreSQL this
                    would be an EXCLUDE constraint; MySQL has no equivalent, so
                    the transaction IS the guarantee.

 INDEX ........ idx_boarding_overlap - written justification in Section 4.
