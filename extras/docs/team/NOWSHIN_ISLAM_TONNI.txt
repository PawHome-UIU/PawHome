1.1  WHY WE CHOSE REACT
--------------------------------------------------------------------------------

Five real reasons, not "it is popular":

1. REUSE.  We have 29 screens. Without React we would write the same button,
   the same input box and the same pop-up dialog on every one of them. In
   React we wrote Button.jsx ONCE and imported it 29 times. Change the button
   style in one file and every screen updates.

2. THE SCREEN FOLLOWS THE DATA.  In plain HTML+JavaScript you have to find
   the element and change it by hand every time something happens. In React
   you change the DATA and React redraws whatever depended on it. Fewer bugs,
   because there is no way for the screen and the data to disagree.

3. SINGLE PAGE APPLICATION.  The browser loads one HTML file once. After that
   React swaps the content when the address changes. No white flash, no full
   reload -- it feels like a phone app rather than a website.

4. READY-MADE ECOSYSTEM.  Routing, charts, icons and HTTP all have mature
   React libraries. We did not have to build any of them.

5. IT LETS THREE PEOPLE WORK AT ONCE.  A React component is just a file. We
   split the project so each person owns whole folders nobody else edits,
   which is why we get almost no merge conflicts.

--------------------------------------------------------------------------------
1.2  HOW REACT ACTUALLY WORKS  (the five ideas)
--------------------------------------------------------------------------------

COMPONENT   A JavaScript function that returns JSX (HTML-looking code).
            Its name starts with a capital letter.
                function PetCard() { return <div>Cooper</div>; }

JSX         HTML written inside JavaScript. Vite converts it to real
            JavaScript before the browser sees it.

PROPS       Data passed INTO a component from its parent. Read-only.
                <PetCard name="Cooper" age="3 months" />

STATE       Data that CHANGES inside a component. Declared with useState.
            When you call the setter, React redraws that component.
                const [open, setOpen] = useState(false);
                setOpen(true);        // -> React redraws

EFFECT      Code that runs AFTER the screen is drawn -- used for fetching
            data. Declared with useEffect.
                useEffect(() => { api.get("/pets").then(...) }, []);
            The empty [] means "run once when the page opens".

WHY IT IS FAST:  React keeps a lightweight copy of the page in memory (the
"virtual DOM"). When data changes it compares old and new, and updates only
the parts that actually differ instead of redrawing everything.

OTHER HOOKS WE USE:
  useMemo         remember a calculated value so filtering does not re-run on
                  every keystroke
  useParams       read the changing part of an address, e.g. the 7 in /pets/7
  useNavigate     move to another page from code, e.g. after a form is saved
  useLocation     read the current address
  useContext      read shared data from anywhere without passing props down
                  through every level -- this is how AuthContext works

1.3  THE ARCHITECTURE  --  how each section provides everything
--------------------------------------------------------------------------------

Three programs run at the same time and talk over the network:

    BROWSER  (React + Vite, port 5174)
        |  Axios request, carrying the login token
        v
    BACKEND  (Spring Boot, port 8081)
        |  JDBC
        v
    DATABASE (MySQL 8.4 in Docker, port 3307)

The browser NEVER touches the database directly. Everything goes through the
backend, because the backend is the only place that can be trusted to check
"are you allowed to do this?"

INSIDE THE FRONTEND there are four layers. Each provides something different:

  PAGES         src/pages/...
                One file = one full screen. A page knows WHAT to show and WHEN
                to fetch. It holds the state and the handlers.

  COMPONENTS    src/components/...
                Reusable pieces. A component knows HOW something looks. It
                takes props and gives back JSX. It does not fetch data.
                  ui/         buttons, inputs, modals -- used by everyone
                  layout/     public nav bar, footer, page frames
                  portal/     the sidebar shell for logged-in areas
                  admin/ staff/ adopter/   pieces used by only that portal
                  pets/ brand/ sections/   shared small pieces

  DATA + API    src/api/client.js   the one place that talks to the backend
                src/lib/            small helpers (address, error text, rules)
                src/data/           placeholder data for screens whose
                                    endpoints are not built yet

  SHELL         index.html -> src/main.jsx -> src/App.jsx
                main.jsx starts React and wraps everything in BrowserRouter
                and AuthProvider. App.jsx lists every route.

THE RULE WE FOLLOW: pages fetch, components display. A component that fetches
its own data cannot be reused anywhere else.

1.5  ROUTING  --  which page shows for which address
--------------------------------------------------------------------------------

THE CONTROL FILE IS  src/App.jsx.  Every address in the whole application is
listed there. If a page is not in App.jsx, you cannot reach it.

  index.html          one empty <div id="root">, loads main.jsx
  src/main.jsx        starts React; wraps the app in
                        <BrowserRouter>   -- the router
                          <AuthProvider>  -- who is signed in
                            <App />
  src/App.jsx         the route table

THE FIVE ROUTE GROUPS:

  PUBLIC   /  /pets  /pets/:id  /features  /services  /about
  AUTH     /join  /login  /register  /forgot-password
           /check-email  /verify-email  /reset-password  /accept-invite
  ADMIN    /admin  /admin/shelters  /admin/users  /admin/analytics
           /admin/reports  /admin/quiz  /admin/settings
  STAFF    /staff  /staff/pets  /staff/applications  /staff/applications/:id
           /staff/care  /staff/boarding  /staff/settings
  ADOPTER  /app  /app/pets  /app/pets/:id  /app/pets/:id/apply
           /app/recommendations  /app/applications  /app/boarding
           /app/boarding/:id  /app/favorites  /app/settings
  404      *

TWO THINGS TO REMEMBER:
  * ":id" is a changing value. /app/pets/7 shows pet 7; the page reads it
    with useParams().
  * The "*" 404 route MUST STAY LAST. React Router picks the FIRST match and
    "*" matches everything -- if it moves up, every page becomes a 404.

1.6  HOW WE STOP AN ADOPTER SEEING THE ADMIN PAGES
--------------------------------------------------------------------------------

TWO LAYERS. Explain both -- the second one is where the marks are.

LAYER 1 -- THE BROWSER (navigation only, NOT security)
  src/context/AuthContext.jsx   holds who is signed in
  src/components/auth/ProtectedRoute.jsx   wraps whole route groups

  In App.jsx:
      <Route element={<ProtectedRoute roles={["ADMIN"]} />}>
        ...all the /admin routes...
      </Route>

  Three outcomes:
      not signed in   -> sent to /login, remembering where they were going
      wrong role      -> sent to their own portal (not an error page -- they
                         are not doing anything wrong, just in the wrong place)
      right role      -> the page renders

  While the app is still asking the server who you are, ProtectedRoute shows
  a spinner. Without that, refreshing on /admin would flash the login page.

LAYER 2 -- THE SERVER (this is the real security)
  backend .../security/SecurityConfig.java   which endpoints need a login
  backend .../security/ScopeGuard.java       which rows you may touch
  backend .../security/JwtAuthFilter.java    reads the token on every request

  Every request carries the token. The backend reloads the real user row and
  decides. A staff member from Shelter A cannot read Shelter B's pets even by
  changing the URL, because ScopeGuard checks the shelter on the row.

THE SENTENCE TO SAY:
  "ProtectedRoute is convenience, not security. Anyone can edit localStorage
   in devtools and write {"role":"ADMIN"} -- and they would get an empty
   admin portal and a wall of 403s, because every request still carries their
   real token and the server reloads their real row."

  That is written in the comment at the top of ProtectedRoute.jsx and
  AuthContext.jsx. It is worth quoting.

  AuthContext also proves it: on boot it calls GET /auth/me with whatever
  token is stored and BELIEVES THE SERVER, not localStorage.

1.7  HOW A BUTTON REACHES THE DATABASE
--------------------------------------------------------------------------------

  src/lib/config.js       the backend address, in ONE place
        export const API_BASE =
          import.meta.env.VITE_API_URL || "http://localhost:8081/api/v1";

  src/api/client.js       one Axios object built on that address. It
                          automatically attaches the login token to every
                          request, and on a 401 (token expired) it clears the
                          token and sends the user to /login.

  A page then does:

      // reading when the page opens
      useEffect(() => {
        api.get("/pets").then(({ data }) => setPets(data));
      }, []);

      // writing when a button is clicked
      const submit = async () => {
        await api.post("/applications", { petId, message });
        setDone(true);
      };
      <Button onClick={submit}>Submit application</Button>

  THE FULL CHAIN:
      click -> api.post -> JwtAuthFilter checks the token
            -> SecurityConfig checks the role
            -> Controller -> Service (the rules) -> Repository
            -> MySQL -> JSON back -> setState -> screen redraws

  WHERE WE ARE: auth, pets, applications, quiz, shelters and admin users are
  wired to the real backend. Boarding, care records, reports and analytics
  still read placeholder files in src/data/ -- those endpoints are the next
  phase. The placeholder data is shaped like the database views, so switching
  each page over is a one-line change, not a rewrite.
