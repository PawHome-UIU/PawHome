DATABASE

  Docker Compose             starts the database with one command

WHY MySQL 8.4 AND NOT OLDER:  CHECK constraints are only ENFORCED from MySQL
8.0.16. Older servers read them and silently ignore them, which is worse than
not having them. Our schema relies on CHECK, so the version is pinned.

WHY TAILWIND 3 AND NOT 4:  version 4 changed how it is configured. Our config
files are written for version 3. Upgrading would break the styling.

A2.  HOW THE WHOLE THING WORKS  (the big picture)
--------------------------------------------------------------------------------

Three separate programs run at the same time. They talk over the network.

    BROWSER  (React, port 5174)
        |
        |  sends a request  (Axios)
        v
    BACKEND  (Spring Boot, port 8081)
        |
        |  reads / writes rows
        v
    DATABASE (MySQL 8.4 in Docker, port 3307)

The browser NEVER talks to the database directly. It always goes through the
backend. That is on purpose: the backend is the only place that can check
"are you allowed to do this?"

PORTS: 3307 database, 8081 backend, 5174 frontend.
3306 is the normal MySQL port, so we moved ours to 3307 to avoid clashing with
any MySQL already installed on the laptop. The backend and frontend ports are
shifted for the same reason.

A5.  HOW ROUTING WORKS  (which page shows for which address)
--------------------------------------------------------------------------------

React is a SINGLE PAGE APPLICATION. The browser only ever loads one HTML file.
React Router looks at the address bar and swaps which component is drawn.
The page never actually reloads, which is why it feels fast.

All routes live in src/App.jsx, in four groups:

  PUBLIC   (anyone)
      /                  landing page
      /pets              browse all pets
      /pets/:id          one pet, signed out
      /features  /services  /about

  AUTH
      /join              pick your role first
      /login  /register  /forgot-password

  ADMIN portal
      /admin             dashboard
      /admin/shelters  /admin/users  /admin/analytics
      /admin/reports   /admin/quiz   /admin/settings

  STAFF portal
      /staff             dashboard
      /staff/pets  /staff/applications  /staff/applications/:id
      /staff/care  /staff/boarding      /staff/settings

  ADOPTER portal
      /app               dashboard
      /app/pets  /app/pets/:id  /app/pets/:id/apply
      /app/recommendations  /app/applications
      /app/boarding  /app/boarding/:id  /app/favorites  /app/settings

  ANYTHING ELSE
      *                  404 Not Found page

TWO THINGS TO REMEMBER:
  * ":id" means a changing value. /app/pets/7 shows pet number 7.
  * The "*" 404 route MUST stay LAST. If it moves up, every page becomes 404.

WHY THE ADOPTER PORTAL IS /app AND NOT /adopter:  it is the address a logged-in
user lives in all day, so we kept it short.


--------------------------------------------------------------------------------
A6.  HOW WE STOP AN ADOPTER SEEING THE ADMIN PAGES
--------------------------------------------------------------------------------

BE HONEST ABOUT THIS. The teacher will ask, and the truth is fine:

  "Right now no route is guarded. The pages show placeholder data, so someone
   typing /admin sees fake numbers, not real records. The real protection is
   built in the next phase."

THE PLAN IS TWO LAYERS. Explain both -- this is the part that scores marks.

  LAYER 1 -- THE BACKEND. This is the real security.
      Every endpoint gets a Java annotation:

          @PreAuthorize("hasRole('ADMIN')")
          public List<Shelter> listShelters() { ... }

      When a request arrives, the backend reads the login token, sees the
      user's role, and refuses with "403 Forbidden" if it does not match.
      This cannot be bypassed from the browser.

  LAYER 2 -- THE FRONTEND. This is only for a tidy experience.
      A <ProtectedRoute> wrapper in App.jsx will hide pages the user should
      not see, so they never click a button that fails:

          <Route path="/admin" element={
            <ProtectedRoute role="ADMIN"><AdminDashboard /></ProtectedRoute>
          } />

THE KEY SENTENCE TO SAY:
  "The frontend guard only hides menus. Anyone can edit React in their own
   browser. The backend check is the one that actually protects the data."

Roles are stored on the user row in the database and put inside the login
token when you sign in.

A8.  HOW BUTTONS WILL CONNECT TO THE API
--------------------------------------------------------------------------------

WHERE WE ARE NOW (say this honestly):
  27 of our 29 pages read from fake data files in src/data/.
  Only LoginPage and RegisterPage actually call the backend.
  The backend REST endpoints are the next phase.

WHY THE FAKE DATA IS NOT LAZY -- this is the good answer:
  The fake data is shaped EXACTLY like the database views return.
  There is a comment at the top of src/data/pets.js that says so.
  That means swapping to the real backend changes ONE line in each page --
  where the data comes from -- not the twenty components that display it.

HOW THE CONNECTION WORKS, IN ORDER:

  1) src/lib/config.js holds the backend address in one place:

         export const API_BASE =
           import.meta.env.VITE_API_URL || "http://localhost:8081/api/v1";

  2) src/api/client.js creates one Axios object using that address, and
     automatically attaches the login token to every request:

         api.interceptors.request.use((config) => {
           const token = localStorage.getItem("token");
           if (token) config.headers.Authorization = `Bearer ${token}`;
           return config;
         });

     It also watches the replies. If the backend says "401 Unauthorized"
     (token expired), it clears the token and sends the user to /login.

  3) A page imports that object and uses it.

     READING data when the page opens:

         useEffect(() => {
           api.get("/pets").then(({ data }) => setPets(data));
         }, []);

     SENDING data when a button is clicked:

         const submit = async () => {
           await api.post("/applications", { petId, message });
           setDone(true);
         };
         ...
         <Button onClick={submit}>Submit application</Button>

  4) The backend receives it:

         POST /api/v1/applications
           -> Spring checks the token and the role
           -> Controller receives it
           -> Service applies the rules
           -> Repository saves the row in MySQL
           -> sends JSON back
           -> React updates the screen

SO THE FULL CHAIN IS:
    button click -> api.post -> Spring Controller -> Service -> Repository
                 -> MySQL -> back up the same path -> screen updates

--------------------------------------------------------------------------------
B3.  QUESTIONS THE TEACHER MAY ASK ME
--------------------------------------------------------------------------------

Q: Does your login actually work?
A: The page sends a real POST to /api/v1/auth/login. The backend endpoint is
   not built yet, so it returns an error. The form, the validation and the
   error handling are finished. These are the only two pages already wired.

Q: Why can a guest browse pets but not apply?
A: Browsing is what makes someone want to sign up, so we do not block it.
   The gate is at the application, where we need to know who the person is.

Q: What stops someone typing /app/applications and seeing another user's data?
A: Nothing on the frontend yet -- no route is guarded. The pages show fake
   data, so there is nothing real to leak. The real protection is
   @PreAuthorize on the backend endpoints, which the browser cannot bypass.

Q: Why is the eligibility quiz a pop-up instead of a page?
A: It interrupts a task; it is not a destination. Keeping the pet visible
   behind it means the user does not lose their place.

Q: What is ":id" in /app/pets/:id?
A: A changing value. /app/pets/7 shows pet 7. React Router reads it with
   the useParams hook and the page fetches that pet.

Q: Why does PetCard live in components/pets/ and not in your adopter folder?
A: Because two different areas use it -- the public browse page and the
   adopter portal. Putting it in a shared folder stops us writing it twice.

Q: How would you connect the pet list to the real API?
A: Replace the import from data/pets.js with:
       useEffect(() => { api.get("/pets").then(r => setPets(r.data)); }, []);
   Nothing else in the page changes, because the fake data already has the
   same shape as the API response.

Q: What is left to do in your part?
A: The auth endpoints in Java, token storage, ProtectedRoute, and replacing
   the fake data on the nine adopter pages.
